# 折叠计数 App：Apple 开发能力调研

调研日期：2026-10-23，随规划 v0.4 更新。目标：判断面向 App Store 的 iPhone Duo 折叠计数工具能否实现自动统计，以及用户明确要求的跨 App 常驻右侧栏。

后续决策补充（规划 v0.5）：用户已接受先做普通 App。已创建支持演示模式的 SwiftUI 工程，原有 API 与后台限制结论不变；普通 App 体验版不再等待全局栏接口。

2026-10-24 补充（规划 v0.7）：用户已追加桌面 / 锁屏小组件，原生 WidgetKit 扩展已接入 App Group 统计投影与时间线。下文“尚未选定 / 仅为备选”保留原调研当时的语境；当前交付见 [小组件说明](桌面与锁屏小组件.md)。该追加不改变全局右侧栏与后台采集的结论。

## 结论

**已确认公开的铰链状态与角度接口，可作为自动计数的数据输入；尚无证据支持全天、跨 App、锁屏及退出后无漏记的统计承诺。**

**用户另已明确全局右侧栏需在其他 App 中常驻。此次未找到允许第三方 App 向该系统栏添加统计项的公开接口；本 App 工具栏不能作为其实现。** 实时活动、小组件与 Controls 的可用位置和时限另有限制，只列备选，尚未选定。

本次直接核对 Apple Developer 官方文档、本机 iOS 27.1 SDK 公开头文件及 Swift 接口，并对最小调用做了类型检查。未运行真机测试，也未验证系统运行时事件交付。

| 能力 | 调研结果 | 对产品的影响 |
| --- | --- | --- |
| 当前铰链状态 | 已有公开 API | 可区分合拢、半开、完全展开；UIKit 另有 unknown |
| 当前铰链角度 | 已有公开 API | 可显示姿态；不宜依赖固定频率或精度计数 |

| 半开连续停留 1 秒才计数 | App 业务规则，用户已确定 | 使用连续有效区间与单调计时实现，不是 Apple 的角度或停留阈值 |
| 合拢外屏、半开/全开内屏的前台展示切换 | 需求已明确，实际接管与事件连续性未实测 | 切换展示复用同一份计数与目标，不把视图重建当成新动作 |
| Duo 跨 App 常驻右侧栏 | 此次官方文档与 SDK 未找到对应公开扩展点 | 用户需求已明确，当前不能承诺交付；不以 App 内工具栏替代 |

| 实时活动 / 小组件 / Controls | 官方提供 App 外展示或操作入口 | 仅为备选；位置、持续与刷新不等同全局右侧常驻，也不保证连续铰链采集 |
| 前台合拢时是否完整交付 closed | 未实测 | 合拢可能伴随屏幕、视图层级或场景变化，是第一验证点 |

| App 未运行期间的历史查询 | 本次所查接口中未发现 | 不能靠重新打开 App 补齐此前的全部开合 |
| 后台、挂起、锁屏及强制退出后持续统计 | 官方资料未提供这类保证，未实测 | 发布前必须验证；不能由前台接口存在推导成立 |
| 次数与折痕程度、剩余寿命的换算 | 本次未获得可靠依据 | 产品提供使用记录，暂不提供健康度或寿命预测 |

“未发现”限定于此次搜索的官方文档及 SDK，不等于证明所有可能的系统能力都不存在。

## 已核实的公开接口

### UIKit：UIHinge / UIHingeInteraction

- iOS 27.1 起提供。
- `UIHinge.status`：`.unknown`、`.closed`、`.partiallyOpen`、`.fullyOpen`。
- `UIHinge.angle`：单位为弧度。
- 将 `UIHingeInteraction` 加入 `UIView`，通过 handler 中 `update.hinge` 获得状态。
- 初次注册会收到初始状态；初始状态是快照，不能当作新发生的一次折叠。
- 当 interaction 离开能够提供铰链更新的视图层级，`hinge` 为 `nil`。

官方对角度的说明：

> “The rate and granularity of angle updates are system policy and can change based on system state…”

官方建议：只需判断合拢、半开、完全展开时，优先用 `status`。

官方对 `isEnabled` 的说明：

> “While disabled, the interaction’s handler is not called for hinge updates, and any updates that occur are not queued.”

重新启用后给出可用的当前状态。这直接说明**主动停用监听期间不能依赖该接口补发事件**；它本身没有完整说明每一种后台、锁屏情况的交付行为，这些仍要分别实测。

### SwiftUI：onHingeChange / DeviceHinge

- iOS 27.1 起提供。
- `View.onHingeChange(isEnabled:_:)` 接收旧、新 `DeviceHingeContext`。
- `DeviceHingeContext.hinge` 是可选值；缺失时不能把它当作合拢或零次。
- `DeviceHinge` 提供 `status` 与 `Angle` 类型的 `angle`；展示角度可使用 `.degrees`。
- 修饰符挂在稳定的根视图，避免切换 App 内页面反复创建采集入口。
- 一个设备只设一个计数入口，避免多个视图或场景对同一折叠重复计数。

SwiftUI 与 UIKit 是同一类数据的两条接入途径，不代表两个可独立累加的来源。

### 状态与角度边界：补充核查

本次进一步读取了 UIKit 状态枚举、各状态说明及 SwiftUI 的角度属性文档。

| 状态 | 官方定义 | 角度边界 |
| --- | --- | --- |
| closed | 铰链已合拢 | 本次所查文档未公开固定分界角度 |
| partiallyOpen | 铰链部分展开 | 本次所查文档未公开固定起止角度 |
| fullyOpen | 已打开到设备所允许的最大程度 | 不应硬编码为必须等于 180° |
| unknown | 铰链状态未知，UIKit 枚举提供 | 不属于物理开合姿态 |

SwiftUI 的 DeviceHinge.Status 公开 closed、partiallyOpen、fullyOpen 三种状态；context.hinge 缺失是另外的数据可用性情况，不能直接等同合拢。

角度是数值，而非几个固定档位：UIKit 用弧度，SwiftUI 用 Angle（可通过 degrees 读取度数）。此次所查文档未给出统一数值上下限或状态对应的固定角度区间。0° 合拢、90° 直角、180° 展平只能作为几何示意，不能当作本 API 已验证的端点和阈值。官方还说明状态会结合当前角度与设备朝向判定。

产品计数优先使用系统 status；如果业务需要自定义有效展开角度，应在真机验证后将其明确作为 App 自己的规则，并处理状态抖动，不宣称是 Apple 官方分类。

## 后台能力不能填补的缺口

官方 Background Tasks 文档描述的是系统调度的任务与有限的后台执行机会。它没有为铰链提供历史记录数据库或每次折叠触发的后台唤醒机制。

即使使用较新的 `BGContinuedProcessingTask`，官方也要求任务由用户操作发起、在前台启动、报告进度，并允许取消。它用于完成有结束条件的工作，不能据此承诺永久监听；任务获得执行时间也不等于视图关联的铰链回调一定有效。

小组件、Live Activity、快捷指令可以是后续展示或手动输入入口；本次未查到它们能为该场景提供全天铰链事件的依据。不能把前后台切换、屏幕尺寸变化或设备旋转直接换算成折叠次数。

## Duo 全局右侧栏补充核查

用户已明确，希望切换到其他 App 后系统右侧纵向栏仍常驻显示折叠、展开次数。此前按 App 内工具栏做的方案不满足此范围，已在 [全局右侧栏需求与可行性](纵向工具栏方案.md) 中修正。

已核实 `ToolbarItem`、`axisBehavior(.verticalPreferred)`、`toolbarVerticalBehavior(.automatic)`、`toolbarVerticalCompressionBehavior` 与 `toolbarVerticalEdge`。后者是只读环境值：由设备与 locale 决定首选侧，非空不代表当前实际可见，无纵栏的上下文可返回 nil。纵向优先是布局偏好，不是强制固定物理右侧的 API。

继续核查 ActivityKit、WidgetKit、其更新说明、Controls 文档及 SDK 中的相关公开声明，没有找到面向该全局右侧栏的公开入口。也检查了 ExtensionKit 的公开宿主接口，不能从通用扩展机制推导存在系统侧栏扩展点。此结论限定于此次核查范围。

| 备选能力 | 官方范围 | 与用户要求的差异 |
| --- | --- | --- |
| 实时活动 | 可在灵动岛、锁屏等位置显示；按官方文档单次最多活跃 8 小时，结束后锁屏最多额外保留 4 小时，也可能更早移除 | 不能指定右侧纵栏或保证全天常驻；适用性与实际呈现需验证 |
| 小组件 | 系统位置中的信息展示；扩展即使可见也不持续运行，时间线和刷新受系统预算调度 | 不覆盖在其他 App 右侧，也不保证每次开合即时更新 |
| Controls | 在控制中心、锁屏与操作按钮等位置提供按钮或开关 | 属于用户调出的入口，不是常驻任意位置的统计栏 |

官方 Live Activities 文档还明确提到 iPhone Duo 可能采用受宽度限制的灵动岛呈现，建议紧凑内容适配约 28 pt 直径的圆形区域。这是灵动岛适配要求，不是新增右侧系统栏接口；也不能承诺三类数字同时完整展示。ActivityKit 更新说明中的 Mac 菜单栏能力不适用于推导 iPhone 系统侧栏能力。

**全局显示与连续采集分开验收。** 即使实时活动在别的 App 使用期间可见，仍只能更新有可靠来源的数据，不能据此证明铰链回调会在后台、挂起、锁屏或退出后持续交付。备选方案尚未被用户选定，本次没有新增活动或小组件工程。

`VerticalBarAPIProbe.swift` 仅通过本 App 工具栏类型检查。栏内数字、自定义内容的压缩、实际所在侧与可用姿态都未运行验证，更没有验证跨 App 存续。

## 正式开发前的验证任务

建议先安排约 2—3 个工程工作日做能力验证；这是工作量预算，前提是已有可用的 iPhone Duo 真机与 iOS 27.1，结果不作时间保证。

| 顺序 | 验证任务 | 证据与判定 |
| --- | --- | --- |
| 1 | 记录原始状态、角度、单调时间、scene 状态、hinge 是否缺失 | 建立最小诊断界面和导出日志，暂不做完整产品 UI |
| 2 | 前台开合、半开停留不足/恰好/超过 1 秒、全开收回半开、快速开合 | 与人工记录逐次对照；区分经过半开与有效停留，确认 closed 交付与视图切换顺序 |
| 3 | 切到其他 App、回桌面、锁屏、挂起、系统回收、强制退出 | 分开记录漏记、延迟和恢复表现，短时后台结果不能外推全天 |
| 4 | 主动关闭再开启监听，期间多次开合 | 核对官方“不排队”语义；恢复快照不得伪造历史次数 |
| 5 | 重启设备与 App、低电量、关闭后台刷新、更新系统 | 确认存储与覆盖区间，并记录系统差异 |
| 6 | 查系统是否另有公开累计/历史接口 | 如有，补充正式文档、授权条件、时间戳粒度、回补和去重验证 |
| 7 | 对照当时 App Review Guidelines | 确认 API 用途、后台模式、商店文案与实测范围一致 |
| 8 | 合拢外屏、半开/全开内屏的显示与场景重建 | 三态主数字、目标映射正确；计时不被页面重建重复启动；切换中断时不伪造记录 |
| 9 | 全局展示依据与范围 | 如取得新的右侧栏公开文档，核实扩展点、允许内容、位置、持续与可用场景；若改选实时活动 / 小组件，另行验证，不用 App 内工具栏结果代替 |

测试不需要为了凑大样本专门反复折叠设备。先用小规模有记录的验证，再结合正常使用观察；软件状态机的大量边界测试使用合成事件。

建议的工程验收目标：合成事件全部通过；支持场景中，人工标注样本的计数精确率与召回率分别至少 99%，并披露样本量与场景。该数字是待验证的研发目标，不是已有结果，也不能证明无漏记。

### 验证后的产品决策

1. **找到可靠的系统累计/历史来源**：再确认是否有按日时间戳，以及退出后的回补能力。仅有累计数时，只能可靠展示累计或区间差，不能把跨日差额分摊为每日真实数据。
2. **只有视图关联的实时事件**：允许继续做有覆盖范围标识的记录原型。面向公众推广“全天自动计数”前应暂缓立项，重新评估受限记录的用户价值。
3. **前台合拢事件也不完整**：先停止自动计数产品化，提交开发者技术问题或寻找官方支持。手动记账属于产品方向变化，需单独决策。

以上是数据源分支，不能单独决定完整产品可交付。全局右侧栏目前仍缺少公开实现依据；如始终坚持此栏位，需取得官方接口依据后再推进完整 UI。如考虑备选，应先确定位置、持续方式与刷新差异。当前可以继续做采集诊断，不将“实时活动可显示”当成已解决全部核心要求。
